# ADR 0001: docs の日英二言語化方針

- Status: proposed
- Date: 2026-06-12
- Deciders: (ユーザーが承認時に記入)

## 背景

`docs/` 配下は初期 (M1〜M3) には英語、方針転換 (2026-06-11) 以降は日本語、と文体が混在していた。Issue 起案・PR レビューでの認知コスト、外部閲覧者 (英語話者の研究室訪問者・OSS リポとしての将来配布) の双方を考えると、片言語に寄せるよりも明示的な二言語並列が望ましい。配布の現実解は MkDocs Pages 等のサイト構築ではなく、GitHub 上で直接閲覧できる軽量な構造である。

## 決定

1. **構造**: ディレクトリ分離方式を採る。`docs/ja/` と `docs/en/` に文書を並列配置し、`docs/` 直下の元ファイルは「両言語版へリンクするだけのスタブ」に置き換える。
2. **言語スイッチャー**: 全両言語版文書の冒頭 (タイトル直下) に次の 1 行を入れる。日本語版と英語版で対のパスを書き分ける:

   日本語版 (`docs/ja/<path>/foo.md`):

   ```
   Language: [日本語](foo.md) | [English](../../en/<path>/foo.md)
   ```

   英語版 (`docs/en/<path>/foo.md`):

   ```
   Language: [日本語](../../ja/<path>/foo.md) | [English](foo.md)
   ```

   相対パスは各文書の階層深さに応じて調整する (`docs/ja/README.md` のように `<path>` が空なら `../en/README.md` のように 1 段になる)。日本語版 → 英語版・英語版 → 日本語版どちらからもクリック 1 回で到達できること。
3. **対象範囲**:
   - 両言語化する: `docs/` 配下の全ライブ文書 (`docs/README.md`、`docs/plans/`、`docs/research/`、`docs/decisions/`) と歴史記録 (`docs/m*-*.md`、`docs/session-*.md`、`docs/migration-plan.md`、`docs/legacy-index.md`)。リポ直下 `README.md` も両言語化する。
   - 両言語化しない: `CLAUDE.md` (Claude ロード専用、日本語のまま)、`.claude/agents/` と `.claude/commands/` の各定義 (Claude 専用 system prompt)。
4. **CLAUDE.md の Import**: `@docs/plans/2026-06-11-platform-pivot.md` のような import 行は日本語版 (`@docs/ja/plans/...`) を指す。Claude は日本語版を正本として扱う。
5. **スタブ化の体裁**: 元ファイル (`docs/README.md` 等) は最小 (10 行以内) のスタブとし、両言語版への相対リンクと最低限のディレクトリ説明のみを含む。
6. **新規文書の作成規約**: 今後新規に作成する `docs/` 配下文書 (M4-R 以降の `m*-*.md`、新規 ADR、新規 plan、新規研究等) は最初から `docs/ja/<path>` と `docs/en/<path>` を並列で生やす。スタブも合わせて生成する。

## 採用しなかった案

- **サフィックス方式** (`docs/foo.ja.md` `docs/foo.en.md`): 同一ディレクトリで対が並ぶため発見性は高いが、`docs/plans/` のような階層配下では一覧時に対の片方を見落としやすい。ディレクトリ分離の方が「片言語丸ごと」の認知が容易と判断した。
- **MkDocs + mkdocs-static-i18n + GitHub Pages**: 読み体験は最良だが `mkdocs.yml` の保守と CI/CD 設定が増え、現在のリポ規模・運用人数 (1 名) では割に合わない。将来配布フェーズで再評価する余地は残す。
- **同一ファイル内に日英並列**: 編集時の差分が膨らみ、片方だけの更新を防ぐ機構もない。却下。

## 結果

得るもの:

- 外部閲覧者 (英語話者) と国内協力者 (日本語話者) の双方が GitHub 上で直接読める
- ADR・方針文書を更新する際、両言語の差分が PR diff で明示される (片方だけ更新の事故を発見しやすい)

失うもの (あるいはコスト):

- 文書 1 件あたりのメンテナンス工数が約 2 倍。Issue #13、#14、#15 で初回移行を実施した後も、新規追加・更新時に両方を揃える運用負担が継続する
- 初回両言語化作業の総量は (現在の 13 文書 + 新規 ADR 群) × 2 で、Issue #13〜#15 を通じて段階的に消化する

後続作業:

- Issue #13 (リポ直下 README 両言語化)
- Issue #14 (ライブ文書: docs/README, plans, research, decisions)
- Issue #15 (歴史記録: m*-*.md, session-*.md, migration-plan, legacy-index)
