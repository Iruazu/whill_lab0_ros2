# ADR 0001: bilingualisation policy for docs (Japanese / English)

Language: [日本語](../../ja/decisions/0001-docs-i18n.md) | [English](0001-docs-i18n.md)

- Status: accepted
- Date: 2026-06-12
- Deciders: Iruazu (accepted 2026-06-13)

## Context

The voice of files under `docs/` has been mixed: initial documents (M1-M3) were English, and documents from the 2026-06-11 pivot onwards are Japanese. Considering the cognitive cost during issue drafting and PR review, and the needs of external readers (English-speaking visitors to the lab, and the possibility of future OSS distribution), explicit bilingual parallelism is preferable to converging on a single language. The realistic distribution option is not a site builder such as MkDocs Pages, but a lightweight structure that is readable directly on GitHub.

## Decision

1. **Structure**: Use directory separation. Place documents in parallel under `docs/ja/` and `docs/en/`, and replace the original files directly under `docs/` with stubs that only link to the two language versions.
2. **Language switcher**: Place the following one line at the top of every bilingual document (right under the title). Differentiate the relative paths between the Japanese and English versions:

   Japanese version (`docs/ja/<path>/foo.md`):

   ```
   Language: [日本語](foo.md) | [English](../../en/<path>/foo.md)
   ```

   English version (`docs/en/<path>/foo.md`):

   ```
   Language: [日本語](../../ja/<path>/foo.md) | [English](foo.md)
   ```

   Adjust the relative depth based on each document's location (when `<path>` is empty, as in `docs/ja/README.md`, the path becomes a single hop such as `../en/README.md`). Either direction (Japanese to English, English to Japanese) must reach the other in one click.
3. **Scope**:
   - In scope: every live document under `docs/` (`docs/README.md`, `docs/plans/`, `docs/research/`, `docs/decisions/`), the historical records (`docs/m*-*.md`, `docs/session-*.md`, `docs/migration-plan.md`, `docs/legacy-index.md`), and the repository-root `README.md`.
   - Out of scope: `CLAUDE.md` (loaded only by Claude; stays in Japanese), and the definitions under `.claude/agents/` and `.claude/commands/` (Claude-only system prompts).
4. **CLAUDE.md imports**: Import lines such as `@docs/plans/2026-06-11-platform-pivot.md` point to the Japanese version (`@docs/ja/plans/...`). Claude treats the Japanese version as the source of truth.
5. **Stub form**: Each original file (`docs/README.md` etc.) becomes a minimal stub (within 10 lines) containing only relative links to the two language versions and a minimal description of the directory.
6. **Rule for new documents**: From now on, new documents under `docs/` (the `m*-*.md` from M4-R onwards, new ADRs, new plans, new research, etc.) are created with `docs/ja/<path>` and `docs/en/<path>` in parallel from the start, and the stub is generated together.

## Alternatives considered

- **Suffix style** (`docs/foo.ja.md`, `docs/foo.en.md`): Discoverability is high because the pair sits in the same directory, but under hierarchies such as `docs/plans/` it is easy to miss one side of the pair when listing. Directory separation makes "the entire single-language view" easier to grasp.
- **MkDocs + mkdocs-static-i18n + GitHub Pages**: Reading experience is best, but maintaining `mkdocs.yml` and adding CI/CD does not pay off at the current repo size and headcount (one). Leave room to reconsider at a future distribution phase.
- **Both languages in the same file**: Inflates edit diffs, and there is no mechanism to prevent updating only one side. Rejected.

## Consequences

Gained:

- External readers (English speakers) and domestic collaborators (Japanese speakers) can both read directly on GitHub.
- When ADRs and policy documents are updated, the diff in both languages shows up in the PR review (making single-side updates easier to catch).

Lost (or cost):

- Per-document maintenance roughly doubles. Even after the initial migration via Issues #13, #14, and #15, the operational burden of keeping both sides aligned on additions and updates continues.
- The total initial bilingualisation work is (the current 13 documents + new ADRs) × 2, consumed incrementally through Issues #13-#15.

Follow-up work:

- Issue #13 (bilingualise the repo-root README)
- Issue #14 (live docs: docs/README, plans, research, decisions)
- Issue #15 (history records: m*-*.md, session-*.md, migration-plan, legacy-index)
