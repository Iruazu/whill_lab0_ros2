# セッションログ: 2026-05-06 — 実機 CR2 で M2 wrap-up

Language: [日本語](session-2026-05-06.md) | [English](../en/session-2026-05-06.md)

ROS 2 humble スタック上で WHILL Model CR2 を E2E で初めて立ち上げた回。次の人が同じ誤診を再演しないよう、行き止まりも含めて *調査経路* を残す。

## 状況

- ラボ PC を WHILL ルームに移し、`uu-w` (キャンパス HTTP プロキシが解決するのとは別サブネット) に接続。
- システム全体の `HTTP_PROXY` / `HTTPS_PROXY` 環境変数は、USB / ROS 作業に干渉しないよう起動シェルで `unset` した。
- 椅子は USB を繋いだ状態で電源 ON (LCD 点灯、数字 `93` を表示、起動時に LED が赤)。

## 症状

`ros2 launch whill_bringup whill_launch.py` は `/dev/ttyUSB0` をクリーンに開いた。whill ノードは生き続け (マルチスレッド、ログにエラーなし)、`/dev/ttyUSB0` に fd 16 を握り、`ros2 topic list` に `/whill/states/model_cr2` が出た。だが:

- `ros2 topic hz /whill/states/model_cr2` がレートサンプルを返さない
- `ros2 topic echo /whill/states/model_cr2 --once` がタイムアウト
- ドライバ内の `ReceiveDataset1()` が tick ごとに `< 1` を返す — つまり椅子から 1 バイトも届いていない

ホスト側は健全、椅子側が何も送っていない、ということ。

## 誤診 (二度とループしないよう残す)

1. **「赤 LED + 数字表示 = エラーコード」** — 誤り。仕様を見ずに動き、`93` がバッテリ残量に過ぎず起動時の一瞬の赤 LED が通常ブートシーケンスの一部だとオペレータに指摘されて訂正。**教訓: 汎用デバイスの感覚で推測する前にプロトコル PDF を読め**。
2. **「電源 ON の前に USB を挿していたので再 enumerate」** — 電源サイクル後に USB を挿し直した。`/dev/ttyUSB0` は戻ってきたが症状変わらず。挿す順番は原因ではない。
3. **「PL2303 チップ不一致 / ケーブル配線疑い」** — 仕様によれば CR2 通信は D-sub 9pin (Pin2 TXD, Pin3 RXD, Pin5 GND) の RS232C ±12V で、本ラボは自作の 3 線ハーネスを使っている。TX/RX 入れ替えやレベル不整合を疑った。**取り越し苦労**: ハーネスは正しく動く。ホストからはバイトが出ていた (生 `os.write` で 8 バイト書き込み成功)、そして椅子を起こした後はバイトが戻ってきた。ケーブルは原因ではない。

## 根本原因

電源を入れた直後の Model CR2 は `StartSendingData` を受け取っただけでは Dataset1 フレームの送出を**開始しない**。椅子のシリアル通信サブシステムは、ホストが `SetPower(ON)` を送るまで休眠したまま。WHILL Control System Protocol Specification の §5 ("WHILL response data") に書かれているが、上流 `whill-labs/ros2_whill` の `Initialize()` は `StartSendingData` しか送っておらず、`SetPower` を送っていない。

ドライバをループから外し、`SetPower(ON)` のバイト列 (`AF 03 02 01 AF`) を Python の小さな probe で `/dev/ttyUSB0` に 38400 8N2 で直接書き込んで発見した。椅子はすぐに仕様書通りの応答パケット (`AF 02 52 FF`) を返し、その後 33 バイトの Dataset1 フレームを設定値の 400 ms 間隔で送り始めた。

**テスト中に見つけた副作用:** `SetPower(ON)` の後、椅子はホスト制御モードに遷移し、本体ジョイスティックを暗黙のうちに無効化する。フォローアップで `SetJoystick` を `U0=0x01` (kUserControlEnable) で送ると、制御がユーザーに戻る。

## 修正

`Iruazu/ros2_whill` PR #1 のパッチ — `WhillNode::Initialize()` の `StartSendingData` の直前に追加:

```cpp
whill_->SetPowerOn();
usleep(10000);
whill_->SetPowerOn();
usleep(2000);
whill_->SendSetJoystickCommandWithLocal();
usleep(2000);
```

`SetPowerOn()` の 2 回送信は、`OnSetPowerSrv` 内の既存リトライパターンと同形。ROS 側制御経路 (`/whill/controller/cmd_vel` の `SetVelocityCommand`、`/whill/controller/joy` の `SetJoystickCommand`) は今までどおりオンデマンドで椅子をホスト制御に戻すので、ROS 駆動のモーションにリグレッションはない。

## 検証

パッチ済ドライバをビルドした後:

| テスト | 結果 |
|-------|------|
| コールドブート起動 (`SetPower(OFF)` + 6 秒待ちの後) | 手動 probe なしで即 2.5 Hz publish |
| 本体ジョイスティック駆動 10 秒キャプチャ | `right_motor_speed` -1.53…+0.77、`left_motor_speed` -0.76…+1.54、`battery_current` 0…122 |
| `battery_power` 値 | 93、LCD 表示と一致 |
| Dataset1 の `error` フィールド | 0 (故障なし) |
| `power_on` フィールド | 1 |

ログは `/tmp/m2_test.log` (パッチ前、手動 `SetPower` で起こした後) と `/tmp/m2_test_patched.log` (パッチ後) に残してある。

## 教訓

- **デバイス汎用な直感から外挿する前に仕様書を読む**。[`WHILL/whill_control_system_protocol_specification`](https://github.com/WHILL/whill_control_system_protocol_specification) のプロトコル PDF がバイトレベル挙動の単一の真実。本セッションの最初の 1 時間は、ここから始めていればケーブル理論には費やされなかった。
- **オペレータのその場の読みを信用する** — オペレータが「93 はバッテリ」と言った時、自分の「赤 LED + 数字 = 故障」フレームと矛盾した。彼らが正しかった。もっと早く更新すべきだった。
- **ドライバの沈黙はドライバの失敗とは違う**。whill ノードログは最初から最後までクリーンだった。問題は、`ReceiveDataset1` が何も来なくても警告なしに `< 1` を黙って返すこと。将来の改善として、起動後最初の 2 秒など、0 バイトが続いたら警告を出すロギングを足してもよい。
