## identity 外部パラメータでの遠回り

2026-05-07 のコミットは LiDAR↔IMU 外部パラメータを identity に戻していた。その日 1 回だけの replay で、noetic 引き継ぎ値が ~30 秒以内に発散した一方、identity だと有界軌道が出たためだ。一見、noetic 外部パラメータが古い証拠に見えた。

そうではなかった。今日の再現性試験で:

- 同じ `m3_chair_motion` bag を identity 外部パラメータで連続 2 回 replay すると、まったく違う発散軌道が出た (終端ポーズが 4 倍と 7 倍のキロメートル単位、別方向に飛んだ)。昨日の有界結果はマルチスレッディングの幸運に過ぎなかった。
- ユーザーがチャットで、椅子の物理マウントは noetic 時代から触っていないことを確認した。noetic の並進 `[0.104, 0.412, 0.324]` は完全に一致する: LiDAR は椅子の左側 (+0.412 m)、座面クッションの下で IMU から ~30 cm 下 (+0.324 m in z)、わずかな前方オフセット (+0.104 m)。

つまり最初から noetic 値を保つのが正解だった。復元して `gyr_cov` を緩めると、同じ bag が新規 3 run の最もクリーンなもので再現可能な有界軌道を出した。

修正は `bc52e8b`。`whill_localization/README.md` と `docs/m3-bench-data/README.md` の両方にこの遠回りの経緯を書いてあるので、次の人は繰り返さなくて済む。

## 3-run 再現性試験

同じ単純経路 (廊下 + 椅子/机部屋への一度の旋回と、開始点近くへの戻り)、同じ WHILL 速度モード 2、連続する 3 回の 60 秒収録で、各 run の間に椅子を開始位置に戻す。各 run には新しい FAST-LIO インスタンス。

| Run | 収録品質 | Replay 結果 |
|-----|---------|------------|
| run1 | 静止ウィンドウがユーザーのストップウォッチに対してずれた — 椅子が実際に止まる前に記録が始まった | t=9 秒以降発散。iESKF はクリーンな IMU バイアス推定を得られない |
| **run2** | **クリーン静止 + クリーン走行** | **有界、経路長 40 m、最大変位 14 m、ループクロージャ誤差 18 %** |
| run3 | 後半で歩行者が前方 180° 視野を横切った | 歩行者が現れたところで発散。世界地図上の動く特徴量が registration を壊す |

`run2` を 2 回目 replay すると、最初の replay の終端から ~10 m ずれた終端ポーズで、似た形状 (経路長 50 m、ループクロージャ 22 %) になった。この残余ばらつきは FAST-LIO のマルチスレッド kdtree 更新の非決定性。軌跡形状は再現する。

### 教訓

- **収録品質が支配的**。この設定でクリーンな 60 秒走行は十分。雑な静止ウィンドウや予告なしの歩行者は localization を不可逆に壊す。今後の走行は明示的に周知し、静かな時間帯に走るべき。
- **「noetic 外部パラメータは古い」という直感は間違いだった**。物理マウントが変わっていなければ、引き継いだキャリブはまだ有効。再キャリブが要ると仮定する前に、必ずオペレータに確認する。
- **FAST-LIO のマルチスレッディングは非決定的**。同じ bag、同じバイナリ、同じ config、連続 2 replay で 50 m 経路の終端ポーズが ~10 m 違う。iESKF + kdtree の並行性が原因の見込み。当面は受け入れる (M5 は単一 pass 決定性を要求しない)。必要なら後で上流に issue を立てる。
- **live `/Odometry` がスパース (~1.5 Hz) だった**理由は、`fastlio_mapping` が RViz、3 センサドライバ、static TF publisher、3.3 GiB をディスクに書く `ros2 bag record` とホストを共有していたから。`fast_lio_launch.py` 単独に対するオフライン replay では公称 ~7 Hz に戻る。これは更新レートに影響するがポーズ正しさには影響しない — ただし M5 / Nav2 のコントローラが live `/Odometry` を直接 subscribe する可能性があるので、ホスト負荷を減らす (RViz を切る、不要時は RealSense ストリームを切る) か、FAST-LIO を別ホストで走らせるかが必要になるかもしれない。

## `bc52e8b` で見つけて直した 2 つの副次的バグ

- `localization_launch.py` が `IncludeLaunchDescription` で `fast_lio_launch.py` を include していた。内側 launch は `parameters=[LaunchConfiguration('config_file'), …]` を持っていた。wrap されると substitution が黙って空文字列に解決し、params ファイルが `fastlio_mapping` のコマンドラインから落ちていた。FAST-LIO は上流デフォルト (`lidar_type=AVIA`、Livox トピック名) をロードし、最初の Velodyne PointCloud2 で SIGSEGV した。スタンドアロンの `ros2 launch whill_localization fast_lio_launch.py` は、LaunchConfiguration がトップレベルスコープで正しく解決されるので影響を受けなかった。回避策: config パスをハードコード。LaunchArgument は本当に起動時に変わる必要があるものだけに使う。
- `cube_side_length` が上流値の 1000.0 で `filter_size_map` が 0.5 だったため、pcl::VoxelGrid の int32 インデックスがオーバーフローした (1000³ / 0.5³ = 8 × 10⁹ > 2³¹)。症状は連発する `Leaf size is too small for the input dataset` 警告に続く定常状態の "No Effective Points!" ストール。200.0 に下げた。

## 明日最初のステップ (M5 / Nav2)

M4 はマージ済。椅子駆動の `run2` replay が M4 成果物。次のマイルストーンは M5 (Nav2 経由の自律航法)。まずオフライン作業。椅子時間は live 検証フェーズに温存できる。

```bash
cd ~/whill_lab0_ros2
git pull --ff-only
git checkout -b m5/navigation
```

おおまかな順序の提案:

1. **FAST-LIO 出力を Nav2 が期待する TF ツリーに繋ぐ**。FAST-LIO は `camera_init -> body` を publish する。Nav2 は `map -> odom -> base_link` を期待する。FAST-LIO のフレームを remap するか、小さなブリッジノード (`tf2_ros::StaticTransformBroadcaster` か独自リレー) を入れて、`camera_init -> body` から `map -> odom` を作り、`odom -> base_link` は `whill_sensors_bringup` の static TF に任せる。
2. **保存地図を作る**。`pcd_save.pcd_save_en` を true にし、Nav2 が運用する領域をカバーする緩やかなループを走り、PCD を保存する。AMCL / Nav2 の costmap が消費できるよう、2D 占有格子に変換する (例えば `pcd_to_pgm`、もしくは `octomap_server`)。
3. **Nav2 bringup を立てる**。`nav2_bringup` テンプレ launch を独自 `nav2_params.yaml` で使う。保存地図上の local + global costmap + live `/Odometry`。当面は標準の `bt_navigator` と `controller_server` を使う。
4. **live 走行テスト**。RViz で `geometry_msgs/PoseStamped` ゴールを送り、椅子が経路を計画し `cmd_vel` -> `whill_driver` で追従するのを観察する。椅子の駆動特性 (モード 2 の制約) に合わせて costmap inflation、planner cadence、`controller_server` の速度上限をチューニングする。

M5 のクロージング条件: `ros2 launch whill_navigation nav_launch.py` で起動し、RViz で 5 m ゴールを置くと、椅子が計画し costmap の障害物に衝突することなく自律到達する。

## 午後の追記 — M5-a と M5-b を同日に着地

M4 → main のマージ後、椅子を電源 ON、ユーザー着座のままで、`m5/navigation` に M5 サブマイルストーンを 2 つ積んだ。両方ともオフライン側だけなので、椅子は M4 bag が既に取った以上は動かす必要がなかった。

### M5-a — TF ブリッジ (コミット `3de4ea1`)

新 `whill_navigation` パッケージ。`tf_bridge_launch.py` が 2 つの identity な `static_transform_publisher` ノード (`map → camera_init` と `body → base_link`) を追加し、FAST-LIO の `camera_init → body` を、M3 の static TF と組み合わせると Nav2 形状の `map → ... → base_link` チェーンになるようにした。オフラインで run2 椅子 bag を `fast_lio_launch.py + tf_bridge_launch.py` に対して replay し、`tf2_tools view_frames` を取って検証した。スナップショット (`docs/m3-bench-data/frames-m5a-2026-05-08.pdf`) では `map` から RealSense `camera_*_optical_frame` の葉まで、単一のルートツリーが下りているのが分かる。

### M5-b — 保存 PCD (コミット `6d8b299`)

最初の PCD チェックポイント `docs/m5-maps/lab.pcd` (256,478 点、8.2 MB)。新 config フラグ `pcd_save.pcd_save_en: true` と `publish.map_en: true` を立てて run2 を fast_lio に対して replay し、bag が終わったら `/map_save` サービスを std_srvs/Trigger で叩いて作成した。

過程で 2 つの上流 FAST-LIO の癖が分かった:

1. `pcd_save_en: true` を立てるだけでは**何も保存されない**。`publish_frame_world` から `pcl_wait_save` を満たすべきインループ保存経路が `src/laserMapping.cpp` でコメントアウトされている。よってシャットダウンハンドラには書き出すべきバッファ点がない。
2. `pcl_wait_pub` (`/map_save` サービスが書き出すバッファ) は `publish_map()` だけが供給し、これは `publish.map_en: true` の時だけ走る。このフラグはデフォルト off。立てて初めてサービスがデータを持つ。

M5-c への注意: 保存 PCD は FAST-LIO ドリフト区間からの散在点を含む。run2 の有界軌道は原点から ~15 m 以内に収まったのに、バウンディングボックスは X ∈ [-352, +71]、Y ∈ [-69, +323]、Z ∈ [-10, +90] m に達する。M5-c での PCD → 2D 占有格子変換は `nav2_map_server` に渡す前に積極的にクリップする必要がある (XY ボックス、椅子に関係する高さの Z スライス)。

### プロセス汚染のエピソード

15:00 頃、会話の以前のターンからの `ros2 launch` プロセス残留に M5-b オーケストレーションが躓いた — `/tmp/m5b_pcd_save.sh` が異なる Bash 呼び出しで複数回起動されており、kill はフォアグラウンドプロセスにしか当たらず、孤児となった static_transform_publisher と wrap された `ros2 launch` python プロセスが生き残った。症状: 新規 launch ごとにポート / TF が既に取られていると判断された。

リカバリは単純だった — エディタの language server を見逃すため `grep -v antigravity` を加えた `pkill -9 -f` を各プロセスパターンに当てた。複数の launch ファイルが並走する将来の M5/M6 作業のために覚えておく価値がある: `pkill -INT` で `ros2 launch` の子監視を経由して伝播するのを当てにせず、launch ルート pid に対して直接 `kill -9` する方が良い。
