## ユーザー要件の理解

**本日 (2026-07-19) 中に**、Web アプリから配車 (goal 発行) → 走行 → 完了を
実際に使える最小スタックを実装し切る。明日の実機検証でそのまま使う。
スコープは M7 (配車 API) + M8 (Web UI) の**最小合成**。認証・複数台管理・
安全機能追加は out of scope (既存 failsafe/twist_mux をそのまま使い、
デモはユーザー並走・介入前提)。

**本日は実機使用不可**。したがって受入基準は mock NavigateToPose action
server で実機なしに検証可能なものに限る。実機での最終確認 (real Nav2 +
localizer + WHILL) は明日の検証項目 (§引き渡し) に送る。

## 解決すべき問題

M6-R まででスタックは「RViz で initial pose を打ち、CLI で
`ros2 action send_goal /navigate_to_pose` を叩けば走る」状態にある
(M6-R plan §11)。だが北極星 (親方針 §1) の R6 = 「タブレットから目的地指定・
呼び出し」を満たすには、CLI と RViz を人間が触る運用を廃し、Web との間に
**認証・状態同期・ジョブ管理を後で載せられる API 境界** (親方針 §3.5 の
`whill_dispatch`) を挟む必要がある。今日はその境界の最小版と、境界越しに
叩く最小 UI を作る。

行動規範 #4 の帰結として、Nav2 / localizer のノードには一切手を入れない。
配車ロジックは新規 `whill_dispatch` に閉じ込め、Nav2 とは
`NavigateToPose` action の client としてのみ接続する。

## Web 境界 (rosbridge 経由) の interface 一覧

型付き custom interface を作らず標準型で構成する。全て rosbridge websocket
(port 9090) 越しに roslibjs から触れる。

| 方向 | 名前 | 型 | 内容 |
|------|------|----|------|
| Web → ROS | `/dispatch/submit` (topic) | `std_msgs/String` | JSON `{"waypoint":"<name>","type":"goto"\|"recall"}`。goto=搭乗者を地点へ、recall=無人で呼ぶ (今日は挙動同一、type は明日以降の分岐用に残す) |
| Web → ROS | `/dispatch/cancel` (service) | `std_srvs/srv/Trigger` | 実行中ジョブをキャンセル。roslibjs `Service.callService` |
| ROS → Web | `/dispatch/state` (topic, ~5 Hz) | `std_msgs/String` | JSON `{"job_id","phase","waypoint","progress","queue_len","pose":{"x","y","yaw"},"aligned":bool}`。phase ∈ IDLE/QUEUED/ACTIVE/SUCCEEDED/ABORTED/CANCELED |
| ROS → Web | `/dispatch/waypoints` (topic, 1 Hz 再送) | `std_msgs/String` | JSON list `[{"name","label","x","y","yaw"}]`。UI のマーカ描画元 |

**QoS の割り切り**: roslibjs の subscribe は既定 volatile。`transient_local`
(latched) の取りこぼしを避けるため、`/dispatch/waypoints` は latch に頼らず
**1 Hz で定期再送**する (UI 接続タイミングに依存しない)。`/dispatch/state` も
定期 publish なので同様に取りこぼしに強い。

Web は Nav2 の `/navigate_to_pose` を直接叩かない (行動規範 #4)。goal 発行は
dispatch_node が action client として行う。車両位置も `/pcl_pose` を Web に
直接見せず dispatch が `/dispatch/state.pose` に畳み込む (境界の一元化)。

`dispatch_node.py` の責務 (親方針 §3.5 a-d を単一ノードに集約。demo 最小):
- (a) named waypoint 解決: `waypoints.yaml` を読み `name → (x,y,yaw)` に解決
- (b) ジョブキュー: submit を FIFO キューへ。1 件ずつ実行、cancel 対応
- (c) `NavigateToPose` action client: キュー先頭を goal 化して発行、feedback
  (`distance_remaining` 等) を progress に変換、result を phase に反映
- (d) 車両状態 publish: `/pcl_pose` + `/alignment_status` + キュー状態を
  `/dispatch/state` に ~5 Hz で集約 publish

ノード分割は demo 最小のため 1 ノードに集約する。M7 本実装 (認証・複数台) で
gateway / job-manager / state-publisher に割る余地は残す (責務を関数で分離)。

**progress の算出**: goal 発行直後の `distance_remaining` を分母 D0 とし、
`progress = clamp(1 - distance_remaining/D0, 0, 1)`。NavigateToPose feedback の
フィールド名 (`distance_remaining`) は humble の `nav2_msgs` で確認済だが、
初期値 0 や単調でない揺れがありうるため実装で下限クランプと直近最大値保持を
入れる (§リスク)。

## waypoints yaml の置き場所と形式

**置き場所**: `docs/maps/campus/waypoints.yaml`。占有格子・PCD と同じ
`docs/maps/<site>/` 配下に置き、ADR-0005 (maps 規約) の**拡張**として扱う。
localizer / Nav2 と同じ `site` 座標系 (map frame) を共有するため、地点座標は
map frame のメートル値で書く (occupancy.yaml の origin と同じ基準)。

**形式** (schema):

```yaml
# docs/maps/campus/waypoints.yaml
# 名前付き配車地点。座標は map frame [m]、occupancy_cleaned.yaml と同一基準。
# x/y/yaw は 2026-07-20 現地で各地点に WHILL を運び /pcl_pose 実測して差し替える
# (2026-07-19 時点はプレースホルダ。§引き渡し参照)。
frame_id: map
waypoints:
  - name: gate           # 内部 ID (英数字、submit で参照)
    label: 正門           # UI 表示名
    x: 0.0               # [m] placeholder
    y: 0.0
    yaw: 0.0             # [rad]
  - name: bldg7
    label: 7号館前
    x: 0.0
    y: 0.0
    yaw: 0.0
```

dispatch_node は launch 引数 `site:=campus` から
`docs/maps/<site>/waypoints.yaml` を解決する (`nav_launch.py` の
`_resolve_map_yaml` と同じ WHILL_MAPS_ROOT / repo-root 復元パターンを流用)。

## リスクと既知の不確実性

- **リスク: rosbridge の型/QoS 変換**。roslibjs subscribe は volatile 既定で
  latched を取りこぼす — 緩和策: `/dispatch/waypoints` `/dispatch/state` を
  定期再送 (latch 非依存) にする (§interface で既定済)。
- **リスク: NavigateToPose feedback の progress 化**。`distance_remaining` が
  初期 0・非単調・経路再計画で増加しうる — 緩和策: D0 を「最初に得た正の
  distance_remaining」で確定し、直近最大 progress を保持して逆行させない。
  実機では replan で分母が変わる点を明日確認 (下記 U)。
- **リスク: static file server の CORS/mixed-content**。ページは
  `http://host:8000`、ws は `ws://host:9090` — 緩和策: 同一ホスト・非 TLS で
  揃える。タブレットは同一 LAN 前提。https 化は将来課題。
- **リスク: map→pixel 座標変換の誤り** (origin 符号・y 軸反転・解像度) —
  緩和策: occupancy_cleaned.yaml の origin/resolution を UI に直接読ませ、
  既知地点 (map 原点) の描画位置を目視で 1 点校正。
- **不確実性 U1: 実 Nav2 の feedback フィールドと発火タイミング**。mock は
  理想化されている — 解消に必要: 明日 real `/navigate_to_pose` に対して
  feedback を `ros2 topic echo /navigate_to_pose/_action/feedback` で実測。
- **不確実性 U2: waypoint 実座標**。今日はプレースホルダ — 解消に必要: 明日
  現地で各地点に WHILL を運び `/pcl_pose` を記録して yaml 差し替え。
- **不確実性 U3: dispatch 発行の goal が twist_mux/failsafe 経路と干渉しないか**。
  dispatch は Nav2 に goal を渡すだけで `/cmd_vel*` には触れない設計なので
  原理的に非干渉 — 明日 `m6r_preflight.sh` PASS 後に実走で確認。
