## ハードウェア面の発見

### 椅子インストールを跨いで USB トポロジは保たれた

移設前は RealSense と RTL8153 USB-Ethernet アダプタがホストの xHCI コントローラ Bus 002 上にあり、椅子インストール後は Bus 004 になった。WHILL は Bus 003 のままだったがポート番号は変わった。`/dev/whill` と `/dev/imu` は最初の起動から正しく解決した — まさに VID:PID ベース udev ルールが書かれた目的のケース。これが `KERNELS=` の USB パスマッチングではなく udev アプローチを正当化するデータ点。

### RealSense は引き継ぎノートの言う D455 ではなく D435

`dmesg` は `Intel(R) RealSense(TM) Depth Camera 435` と報告し、デバイスの product ID は `0x0B07` (Intel 公式マッピングでは `0b07 = D435`、`0b5c = D455`)。本体側面ラベルでもユーザーが確認。ドライバ的にはこれで何も変わらない — 同じ `realsense-ros` リリースが両方をサポートする — が、M3 文書の複数箇所で訂正が必要だった。

### Velodyne ネットワーク設定

VLP-16 工場出荷 IP は `192.168.1.201`。ホストは netplan 経由で USB-Ethernet アダプタに `192.168.1.100/24` をもらう。Ubuntu Desktop は `renderer: NetworkManager` の netplan を同梱しており、netplan は `/etc/netplan/*.yaml` 間での renderer 混在を拒否するため、追跡テンプレも `NetworkManager` を使う (networkd 専用ホスト向けに切り替える方法はコメントしてある)。椅子上で E2E 検証済: リンク UP、ARP が LiDAR の MAC `60:76:88:10:6b:6b` を解決、ping 0% ロス、`tcpdump udp port 2368` が LiDAR から `255.255.255.255:2368` への `length 1206` パケットを fullrate で流していることを確認。

## ソフトウェア面の発見

### IMU は `LifecycleNode`、configure-then-activate 遷移がレース

上流 `rt_usb_9axisimu_driver` は `configure → activate` 遷移するまで何も publish しない。`imu_launch.py` の最初の版は `EmitEvent + OnStateTransition` でこれを駆動しており、`configure` が return した瞬間 — 実測 ~22 ms 後 — に `activate` イベントを発火していた。

これはベンチでは動いたが、椅子搭載後に壊れた。ドライバの `on_activate()` コールバックは `readSensorData()` を同期呼び出しし、カーネルのシリアルバッファがまだデバイスから完全な ASCII フレームを集めていなければ read は `FAILURE` を返し、ノードは `errorprocessing` に弾かれる。

`69c3980` での修正: `OnStateTransition(goal_state='inactive')` ハンドラと `Transition.TRANSITION_ACTIVATE` の `EmitEvent` の間に `TimerAction(period=1.5)` を挿入。変更後のログ:

```
on_configure() is called.
reached 'inactive', waiting 1.5 s before activate to let the serial
  port buffer a frame.
on_activate() is called.
ros2 lifecycle get /rt_usb_9axisimu_driver  →  active [3]
```

同じパターンは他の USB-serial / CDC-ACM lifecycle ドライバにも当てはまる可能性が高い — M4 で FAST-LIO が追加の前処理 lifecycle ノードを要求するなら覚えておく。

### その他の小さな驚き

- **humble の `ros2 topic hz` は best-effort QoS を自動検出しない**。Velodyne ドライバは sensor-data QoS で publish するので `hz` はサンプルを返さない。`ros2 topic echo --once` は効くし、QoS を合わせた Python subscriber をコードで書いてもよい。
- **RealSense トピックプレフィクスは `/camera/camera/...`**。`rs_launch.py` が親 ns `camera` + ノード名 `camera` を使うので、トピックは二重プレフィクスになる。M4 / M5 の下流 launch は素の `/camera/` ではなくこのプレフィクスを受け入れるか remap する必要がある。

## 明日最初のステップ

M3 はマージ済。ブランチ `m3/sensors` は消えた (ローカル + リモート)。次のマイルストーンは M4 (FAST-LIO 自己位置推定) で、`m3_chair_motion_2026-05-07/` がディスクにあるのでオフラインで進められる。

```bash
cd ~/whill_lab0_ros2
git pull --ff-only
git checkout -b m4/fast-lio
```

その後、おおまかな順序:

1. FAST-LIO の ROS 2 fork (`hku-mars/FAST_LIO`、`ros2` ブランチ) を `whill_lab.repos` に追加。`./scripts/import_upstream.sh` で vcs import + rosdep 解決し、`colcon build --packages-up-to fast_lio`。`ros-humble-pcl-*` の追加 dep が rosdep で引かれる見込み。
2. noetic の FAST-LIO config を移植する。noetic スタック内の該当ファイルは `~/whill_lab0/FAST_LIO/config/velodyne.yaml`。引き継ぐ LiDAR↔IMU 外部パラメータは [`m3-extrinsics-from-noetic.md`](m3-extrinsics-from-noetic.md) にそのまま転記済。トピック名は変わらず — `lid_topic: /velodyne_points`、`imu_topic: /imu/data_raw`。
3. `whill_sensors_bringup/launch/static_tf_launch.py` の identity な `base_link → velodyne` / `base_link → imu_link` プレースホルダを、引き継ぎ外部パラメータと整合する値に置き換える。(注: 引き継ぎ行列は "LiDAR → IMU"。`base_link = imu_link` とすれば `base_link → velodyne` はちょうどその並進 + 回転になる。)
4. `whill_localization` パッケージを作るか、`whill_sensors_bringup` を拡張して、`sensors_launch.py` を include して FAST-LIO ノードを上記トピックに対して起動する launch を書く。
5. まずオフラインで検証: `ros2 bag play m3_chair_motion_2026-05-07 --clock` を FAST-LIO ノードに対してかけ、`/Odometry` (もしくは ROS 2 fork が publish するトピック — `ros2 topic list` で確認) を眺め、軌跡を目で見る。bag の「静止のち走行」構造はちょうど FAST-LIO が期待するウォームアップ形状。

M4 のクロージング条件: bag を再生中ずっと `/Odometry` が更新され続け、軌跡が記録走行をおおむねなぞり、ループ閉じの末尾で終端ポーズが開始ポーズから ~1 m 以内にあること。これで椅子は "ROS 2 で localization できる" 領域に入り、M5 (Nav2) にクリーンに繋がる。

## 教訓

- **VID:PID ベース udev は正解だった**。ラップトップを物理的に再搭載したら USB ポートは動いたが、symlink は保たれた。`KERNELS=` USB パスマッチングを使っていたら、椅子インストールで `/dev/imu` が黙って壊れていた。
- **引き継ぎノートを盲信しない**。元の移行計画にあった「8086:0b07 は D455」は間違いだった。`dmesg` と Intel ID テーブルが権威。30 秒のチェックで早期に気付けたはず。
- **Lifecycle ノードは遷移間にバックオフが要る**。素早い `configure → activate` チェーンは、底のデバイスの data-ready ウィンドウとレースする。`TimerAction` が最も安価な保険。
- **"静止" データはプログラマティックに検証する、感覚ではなく**。最初の静止 bag が汚染されているというユーザーの直感は正しかったし、IMU 統計が裏付けた。`scripts/check_static.py` でこの確認はワンライナーになった。
