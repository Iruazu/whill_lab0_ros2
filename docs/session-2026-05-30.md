## What broke and how we tracked it

### Symptom 1 — RViz says `Frame [camera_init] does not exist`

FAST-LIO-SAM publishes the map TF as `map`, not `camera_init`. Stock
RViz config from FAST-LIO carries `camera_init` because that's the
upstream HKU-MaRS frame name. Fixed by setting Fixed Frame = `map` in
the FAST-LIO-SAM RViz panel.

### Symptom 2 — `Failed to start FAST-LIO-SAM, no /Odometry topic`

`imu_sign_flip` was launching but the source file lacked the executable
bit. `--symlink-install` symlinks the script through to install/, so the
executable bit must already be set on the source. Fixed with:

```bash
chmod +x src/whill_sensors_bringup/scripts/imu_sign_flip.py
```

(Re-build not needed under symlink-install.)

### Symptom 3 — `incompatible QoS / RELIABILITY_QOS_POLICY` warning

`imu_sign_flip.py` initially used `BEST_EFFORT` for both subscribe and
publish (copy-paste of `velodyne_self_filter.py`'s `sensor_data_qos`).
But the rt_usb_9axisimu_driver publishes `/imu/data_raw` with
`RELIABLE` (rclcpp default), and FAST-LIO-SAM subscribes with `RELIABLE`
as well. Changed `imu_sign_flip.py` to `RELIABLE` end-to-end and the
warnings disappeared.

### Symptom 4 — Buried map

User report on the first 2-round drive:

> rviz上に表示させるマップですがあまり良好ではないかと z軸負の方向に
> 建物や木の情報が出ている気がする

`ros2 topic echo /imu/data_raw --once` on the static chair returned
`linear_acceleration.z ≈ -9.6 m/s²` instead of REP-145's expected
`+9.81`. PCMK-G3X reports the gravity vector directly, not the
"force needed to hold the IMU still" (= -gravity) of REP-145. With the
raw signal, FAST-LIO's `grav_align` decides "+Z is down" and the
reconstructed environment is inverted relative to the world frame.

The fix was a small republish node, `imu_sign_flip.py`, that flips the
sign of the linear acceleration (orientation field is preserved
untouched — FAST-LIO does not use it; `orientation_covariance[0] = -1`
already marks it as unavailable upstream). Then
`fast_lio_sam_velodyne.yaml`'s `imu_topic` was switched from
`/imu/data_raw` to `/imu/data_corrected`.

Live re-check: `ros2 topic echo /imu/data_corrected --once` → `z ≈
+9.58`. Map oriented correctly. User confirmed: 「建物もz軸正側に出てる」.

### Symptom 5 — Rotation drift after the accel fix

A second 2-round drive (this time with the corrected IMU) reported:
"直進してそのままバックする" was clean and the asphalt-step bump was
reflected exactly. But "直進してそのまま旋回" diverged — final pose
landed metres ahead of the start.

Hypothesis: the same PCMK-G3X "device convention" reasoning we applied
to the accel was being applied to the gyro by reflex. But the gyro
might already be in REP-145 (right-handed) — and inverting a correct
sign would make the EKF prediction direction disagree with what
LiDAR-scan registration actually observes during a turn. The covariance
fight would inflate, the pose would drift, and rotation specifically
(not translation) would suffer. That matches the symptom exactly.

Test: set `flip_gyro=False` in `sensors_launch.py`. Re-run. Rotation
behaviour improved markedly — final pose now sits "出発点より少し先" of
the start, no more major drift. The accel-only flip is the holding
configuration.

## What the working IMU still tells us

`linear_acceleration` on the corrected topic, static-state:

  x = +0.06 m/s²   y = +2.68 m/s²   z = +9.58 m/s²

A 2.68 m/s² lateral component on a level chair means the IMU board is
mounted with **~16° forward pitch** relative to base_link
(`asin(2.68 / 9.81) ≈ 15.8°`). grav_align absorbs this for SLAM, but
Nav2 will see chair pose as 15.8° forward-pitched until the
`imu_link → base_link` transform reflects the real mount geometry. See
task #34 in `MEMORY.md` (or wherever the live task list is).

### Follow-up — 5 s static measurement on confirmed-flat floor

Sampled `/imu/data_corrected` for 5 s (500 samples, accel σ ≈ 0.02 m/s²
on each axis — truly static):

| quantity | value | reading |
|---|---|---|
| `|a|` | 9.97 m/s² | accel scale healthy (+1.7 % vs g) |
| `pitch` (rotation around IMU X) | **+16.37°** | nose-down forward tilt |
| `roll` (rotation around IMU Y) | **-0.20°** | laterally level |
| gyro x mean | **-1.143 deg/s** | non-zero on a static IMU → gyro X bias |
| gyro y / z mean | -0.03 / +0.16 deg/s | noise floor |

Roll ≈ 0 on a confirmed-flat floor rules out "chair sits on a slope"
and "y-axis accel bias". The 16.37° is real physical mount tilt of the
IMU board. Therefore when `imu_link` is added to the URDF as part of
Phase A-1 finalization, its origin should carry `rpy="0 0.286 0"`
(0.286 rad ≈ 16.37°). Logged as task #34.

Separately: the **-1.14 deg/s gyro X bias** is independent of the mount
(a static IMU should read zero on every axis regardless of orientation).
FAST-LIO's filter mostly absorbs it via LiDAR feedback, but a long
quasi-static segment could let it leak into pitch. Tracked as a new
follow-up: optional `gyro_bias` param on `imu_sign_flip.py` that
subtracts a constant from each axis before republishing.

## Reproduce from a fresh shell

```bash
cd ~/whill_lab0_ros2
source install/setup.bash
mkdir -p src/third_party/FAST_LIO_SAM/PCD \
         src/third_party/FAST_LIO_SAM/KEY_FRAMES/scans \
         src/third_party/FAST_LIO_SAM/IMU_POSES
# T1
ros2 launch whill_sensors_bringup sensors_launch.py
# T2 (after T1's IMU activates)
ros2 launch whill_localization fast_lio_sam_launch.py
# T3 (sanity)
ros2 topic echo /imu/data_corrected --once   # z ≈ +9.6 m/s² static
ros2 run tf2_ros tf2_echo map base_link
```

Drive a short out-and-back; the `KEY_FRAMES/global.pcd` is written
automatically on Ctrl+C of T2.
