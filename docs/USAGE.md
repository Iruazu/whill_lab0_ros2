# USAGE — 使い方

配置済み(`/agents` で 6 体見える状態)の前提。配置手順は `SETUP.md`。
このリポで 6 エージェント体制を動かして成果を出すための作業ガイド。

---

## 1. 動かし方の全体像

**司令塔(メインの Claude)+ 6 部隊** という構造。

```
あなた ──> 司令塔 ──(委譲)──> 6 エージェント
```

各エージェントは独立した context window で動くので、調査の生データや実装の試行錯誤が司令塔の文脈を汚さない(要約だけ返る)。

**あなたが直接話すのは司令塔だけ。** エージェントを名指しする必要はない。「何をしたいか」を言えば、司令塔が適切な部隊に割り振る。

---

## 2. 基本の 3 モード

| やりたいこと | コマンド | 流れ |
|------------|---------|------|
| 作りたい・移植したい | `/port-feature <機能>` または `/plan <要件>` | 計画 → **承認** → 実装 → レビュー |
| 動かない・おかしい | `/debug <現象>` | 再現 → 仮説 → 検証 → 修正 |
| どれがいい・どうやる | `/research <対象>` | 複数ソース比較 → 推奨 |

普通の相談はコマンド無しでそのまま入力してよい(司令塔が自動振り分け)。

---

## 3. ワークフロー実例(このリポの実課題)

### 実例 1: 旧実装の移植 — 学内自律走行

```
/port-feature 学内自律走行
```

内部の流れ(あなたは要所だけ介入):

1. `legacy-archaeologist` が旧リポを調査(全主張に `file:line` 付き)
2. `research-analyst` が ROS 2 での対応手法を調査(例: move_base → Nav2 Waypoint Follower)
3. `pm-orchestrator` が phase 計画を `docs/plans/` に保存
4. **← ここで承認を求めて止まる**(計画を読んで承認 or 差し戻し)
5. 承認後 `ros2-implementer` が phase ごとに実装
6. `code-reviewer` が自動レビュー(重大指摘は実装へ差し戻し)
7. あなたへ: 変更サマリ + 実機検証手順 + 残課題

**あなたの仕事は step 4 の承認と step 7 の実機検証だけ。**

### 実例 2: バグ調査 — FAST-LIO の発散

```
/debug m3_chair_motion_2026-05-07 を offline 再生すると 30 秒で /Odometry が止まる
```

`debugger` が再現コマンドを確立 → 仮説表(gyr_cov / extrinsic / VoxelGrid overflow / 鋭い旋回での registration 失敗 …)→ 優先度順に観測 → `file:line` で根本原因特定 → 最小修正 → 元の再生コマンドで検証 → 診断ログ削除。

### 実例 3: 技術選定 — ループクロージャ

```
/research FAST-LIO 系でループクロージャを足す選択肢を比較。VLP-16 + chair-mounted IMU、humble、velodyne_whill.yaml で運用中
```

候補(FAST-LIO-SAM / FAST_LIO_LC / LIO-SAM / 自前 PGO)をライセンス・humble サポート・既存設定との整合・導入コストで比較 → 推奨。そのまま `/plan` に渡せる。

### 実例 4: レビュー

```
/review src/whill_navigation/config/nav2_params.yaml
```

未コミット差分全体なら `/review uncommitted`。重大 / 改善余地あり / 好みの問題 に分けて指摘。

## 4. 計画の承認(品質の決定点)

実装後に直すより、計画段階で軌道修正する方が圧倒的に安い。`pm-orchestrator` の計画を読むときの確認:

- [ ] 受け入れ基準が**観測可能**か(「動く」ではなく「`/cmd_vel` が publish される」)
- [ ] Phase の順序が依存関係的に正しいか(マップ品質に依存する phase が再キャプチャより前に来ていないか)
- [ ] 実機検証が必要な phase が明示されているか
- [ ] 旧実装を盲目コピーせず ROS 2 の現代パターンに作り直す方針か

差し戻しは普通の言葉でよい:

```
Phase 2 と 3 を入れ替えて。マップが汚いままだと Phase 3 の検証ができない
```

---

## 5. セッション管理(Max プラン)

レート上限は気にせず長く回せるが、1 セッションを引っ張ると司令塔の文脈は劣化する。

| 状況 | やること |
|------|---------|
| 1 つの課題が片付いた | `/compact` で圧縮、または新セッションに切る |
| 別の課題に移る | 新セッションを開く(前の文脈を引きずらない) |
| 司令塔が筋を見失った | `/rewind` で巻き戻す、または新セッション |
| 複数の調査を同時に | 並列エージェントを使ってよい(例: 旧リポ 3 モジュール同時調査) |

並列の目安: **読み取り・調査は並列 OK、ファイル書き込みは直列**(競合回避)。

---

## 6. 依頼の仕方

精度を上げる:
- **観測事実を渡す**: 「動かない」より「`/Odometry` が 30 秒で止まり、`No Effective Points!` が出続ける」
- **制約を 1 行**: 「実機検証は自分でやるので手順を明示して」「`src/third_party/` は触らないで」
- **不確実な前提を明言**: 「extrinsic が正しいか自信がない」→ debugger が真っ先に疑う

やらなくてよい:
- 細かい実装方法の指定(エージェントが既存コードに合わせる)
- どのエージェントを呼ぶかの指定(司令塔が判断)
- 丁寧な前置き(事実が多いほど良い)

## 7. 成果物の置き場所

作業は文脈に消えず、リポに資産として残る。

| 成果物 | 場所 |
|--------|------|
| 実装計画 | `docs/plans/` |
| 技術判断 (ADR) | `docs/decisions/` |
| 旧リポ調査 | `docs/legacy-findings/` |
| 技術調査 | `docs/research/` |
| コード | `src/whill_*/` |

git にコミットして蓄積すれば、次回以降の司令塔がこれらを参照でき、チームの知識が積み上がる。

---

## 8. 作業中に詰まったとき

| 症状 | 対処 |
|------|------|
| 旧実装を盲目コピーした | 「現代的な ROS 2 パターンに作り直して」と明示。CLAUDE.md の規約を再確認させる |
| 計画が曖昧なまま実装に進む | 「受け入れ基準を観測可能にしてから」と差し戻す |
| 調査が浅い(単一ソース) | 「最低 3 ソースで対立見解も」と指示 |
| デバッグが憶測で直そうとする | 「先に再現してから」と止める |
| 司令塔が自分で全部やろうとする | `/port-feature` 等の明示コマンドか「legacy-archaeologist に調べさせて」と名指し |
| 出力に AI 文体(絵文字・追従) | CLAUDE.md の規約を指摘し直す |

> 配置・`/agents` が出ない等のトラブルは `SETUP.md` を参照。
